# P1 / P3 — security review (2026-11-10)

## P1 — legacy direct read
- The production RLS policies `events_member_read` and `participants_member_read` check session validity but do not scope rows to a group. Both tables were empty when checked.
- The proposed migration revokes `authenticated` SELECT and removes these policies. The service-role backend continues to use the tables; no UI, data or RPC changes.
- Transactional privilege probe on production (rolled back): `authenticated` SELECT = false for both; `service_role` SELECT = true for both.
- **Before deployment:** run full migration suite and integration tests (legacy events, participants, settlements, notifications, accounts Edge, Premium UI); ensure no browser code directly reads either table. Test authenticated REST reads (403), service API legitimate flows, and cross-account isolation. No deployment or merge without acceptance.

## P3 — password / logs
- Supabase Security Advisor warns `auth_leaked_password_protection`. Supabase documentation states the built-in HaveIBeenPwned check is available only on Pro and above. **Do not upgrade the plan automatically.** Keep this as a documented residual risk on Free; consider a privacy-preserving breached-password check in the password-create/change flow only after design and tests.
- Aggregated last-24h logs contain 0 literal `service_role` occurrences in inspected sources. `authorization` and `password` occur in log attributes, but these counts alone do **not** prove credential leakage. Inspect redacted log shapes and ensure token/password values are never logged; do not print raw secrets in reports.
- The 31 `rls_enabled_no_policy` INFO findings are not automatically vulnerabilities: verify lack of direct grants and intended service-only access.
- Security Advisor after deployment, browser smoke tests, and real authenticated cross-account checks remain mandatory.
